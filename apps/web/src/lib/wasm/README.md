# WASM engine bundle (`pdf-engine` → browser)

Feature: pdf-tools-suite — Task 7.1 (Req 37.5, 47.1).

This directory holds the wasm-bindgen bundle for the shared Rust PDF engine
(`crates/pdf-engine`) compiled to `wasm32-unknown-unknown`. The bundle is what
the client processing plane loads inside a Web Worker
(`../engine/worker.ts`) so `Client_Capable` tools run entirely on-device under
Privacy Mode.

## Files

| File | Origin | Committed? |
| --- | --- | --- |
| `pdf_engine.d.ts` | hand-written type surface of the generated module | yes |
| `pdf_engine.js` | generated by `wasm-bindgen --target web` | no (build artifact) |
| `pdf_engine_bg.wasm` | generated by `wasm-bindgen --target web` | no (build artifact) |

The generated `.js`/`.wasm` are build artifacts (see `.gitignore`). The
`.d.ts` is committed so `svelte-check`/`tsc` and the unit tests type the import
even before the binary bundle is generated.

## Generating the bundle (CI / local)

The engine exposes a single JS-callable entry point, `run_tool`, from
`crates/pdf-engine/src/wasm.rs` (gated `#[cfg(target_family = "wasm")]`, so the
native build and `cargo test -p pdf-engine` are unaffected).

Preferred (one step):

```sh
wasm-pack build crates/pdf-engine --release --target web \
  --out-dir ../../apps/web/src/lib/wasm --out-name pdf_engine
```

Two-step fallback (no wasm-pack), which is what CI uses:

```sh
# 1. Compile the cdylib for the browser target.
cargo build -p pdf-engine --target wasm32-unknown-unknown --release

# 2. Generate the JS + trimmed .wasm bindings next to this README.
wasm-bindgen \
  target/wasm32-unknown-unknown/release/pdf_engine.wasm \
  --target web \
  --out-dir apps/web/src/lib/wasm \
  --out-name pdf_engine
```

Pin the tools to the versions matching the crate's `wasm-bindgen` dependency
(`=0.2.100`):

```sh
cargo install wasm-bindgen-cli --version 0.2.100   # or: cargo install wasm-pack
```

> Windows note: on the GNU host toolchain used by this repo
> (`+stable-x86_64-pc-windows-gnu`), installing `wasm-bindgen-cli` / `wasm-pack`
> can fail because their transitive `windows-sys` dependency needs `dlltool` to
> build an import library, which the bundled GNU `dlltool` cannot produce in
> some environments. Generate the bundle in CI (Linux) or with the MSVC host
> where a linker is available. The raw `cargo build --target
> wasm32-unknown-unknown` step above always succeeds and produces the `.wasm`;
> only the `wasm-bindgen` glue step needs the CLI.

## Worker load path

`../engine/worker.ts` imports `init` (default) and `run_tool` from
`../wasm/pdf_engine.js`, calls `await init()` once, then invokes `run_tool` per
message. No network request is made for `Client_Side_Processing`; the `.wasm` is
served as a static asset from the same origin (Cloudflare Pages per the design).
